## 背景

Persona Nexus 是一個學習性質的 AI 角色扮演/戀愛模擬平台，目標是展示如何用微服務架構構建具有「連續對話記憶」的 AI 系統。該平台已完成 80% 的核心功能，現在需要建立完整的規格文檔以確保後續 20% 的開發能維持一致的架構與 API 契約。

---

## 目標 / 非目標

**目標：**
- 建立清晰、可擴展的微服務架構，分離關注點
- 確保安全的認證，使用在 gateway 進行集中式 JWT 驗證
- 實現服務的獨立開發和部署
- 透過兩層系統（短期 + 長期 RAG）支援對話記憶
- 在所有服務間提供一致的 API 契約
- 記錄關鍵架構決策的理由，便於維護

**非目標：**
- 高可用性（HA）或跨多個實例的負載均衡
- 分散式交易或跨服務的 ACID 保證
- 實時 WebSocket 通訊（基於輪詢的聊天是可接受的）
- 進階 API 版本管理或向後相容性策略
- 稽核日誌記錄或合規要求（GDPR、SOC 2 等）
- 基本索引之外的效能最佳化（無快取、無 CDN）

## 決策

### 決策 1：採用微服務架構搭配 Gateway 模式

**內容：**
在單一 API 網關（連接埠 8000）後部署 6 個獨立後端服務。每個服務擁有自己的資料（SQLite 資料庫）和業務邏輯。

**理由：**
- **學習目標：** 展示微服務原則：關注點分離、獨立部署、服務發現
- **可擴展性：** 服務可獨立擴展（例如，如果成為瓶頸，chat-service 可被複製）
- **開發隔離：** 團隊成員可以平行開發不同服務，無需合併衝突
- **責任歸屬：** 每個服務擁有自己的資料結構描述和 API 契約，減少耦合

**考慮過的替代方案：**
- **單一應用：** 初期更簡單，但違反了微服務的學習目標
- **分散式 monorepo：** 會在 6 個服務間引起合併衝突；使用分離 git repo 隔離變更
- **服務 API 版本管理：** 每個服務內部公開 `/api/v1/...`，gateway 重寫 `/resource` → `/api/v1/resource` 以隱藏版本複雜性

**權衡：**
- 複雜性：服務間網路呼叫（例如 auth-service → user-service）比進程內呼叫慢
- 一致性：無分散式交易；每個服務必須處理自己的資料完整性
- 除錯：跨服務追蹤請求需要相關 ID（尚未實現）

---

### 決策 2：Gateway 集中式 JWT 驗證

**內容：**
Gateway 是唯一驗證 JWT 簽名的元件。驗證後，它注入 `x-user-id` 和 `x-user-email` header。後端服務信任這些 header，無需重新驗證 JWT。

**理由：**
- **單一真實來源：** 一個地方更新 JWT 邏輯、輪換祕鑰或新增令牌刷新邏輯
- **減少祕鑰暴露面：** 後端服務不需要存取 `JWT_SECRET`（更小的安全洩露範圍）
- **效能：** 避免每個服務中的冗餘 JWT 驗證
- **無狀態服務：** 後端服務完全不知道 JWT；只關心 header 中的使用者上下文

**考慮過的替代方案：**
- **服務層驗證：** 每個服務獨立驗證 JWT → 更穩健但需要發佈 `JWT_SECRET`
- **令牌自檢：** Gateway 查詢 auth-service 端點驗證令牌 → 增加延遲，需要服務耦合
- **相互 TLS：** 服務透過憑證彼此驗證 → 對學習專案來說過度，增加操作複雜性

**權衡：**
- **安全假設：** Gateway 被假設為值得信任且始終存在；如果 gateway 被入侵，後端容易受到偽造 header 攻擊
- **繞過風險：** 如果後端服務被暴露在網際網路（非僅限 localhost），攻擊者可以繞過 gateway
- **緩解：** 網路層隔離確保服務僅可從 localhost 存取；防火牆規則永不直接暴露它們

---

### 決策 3：服務級資料擁有權搭配 SQLite

**內容：**
每個服務擁有分別的 SQLite 資料庫檔案。資料永遠不會直接共用；服務透過 HTTP API 通訊。

**理由：**
- **封裝：** 防止透過共用資料庫進行緊密耦合（早期微服務中的常見反模式）
- **獨立演進：** 每個服務的結構描述可獨立演進，無需影響其他服務
- **故障隔離：** 一個服務的資料庫故障不會級聯到其他服務
- **學習價值：** 展示為什麼共用資料庫是有問題的

**考慮過的替代方案：**
- **共用 PostgreSQL 資料庫：** 對小型專案簡化，但違反微服務原則
- **訊息佇列（例如 RabbitMQ）：** 需要事件驅動架構；對當前範圍來說過度

**權衡：**
- **最終一致性：** 使用者資料在 auth-service 中建立，然後透過 HTTP 呼叫複製到 user-service；如果 user-service 關閉，無原子性保證
- **反正規化：** 某些資料（例如使用者電子郵件）如果需要快速查詢，可能儲存在多個資料庫
- **協調開銷：** 跨多個服務的複雜操作需要謹慎順序化和錯誤處理

---

### 決策 4：三層架構（Controller → Service → Repository）

**內容：**
每個服務強制執行分層架構：
- **Controller：** HTTP 請求/回應處理、輸入驗證、錯誤至 HTTP 狀態碼對應
- **Service：** 業務邏輯、驗證規則、語意錯誤處理（例如 `EMAIL_ALREADY_EXISTS`）
- **Repository：** 透過 Prisma ORM 的資料庫 CRUD 操作

**理由：**
- **關注點分離：** 每層有單一責任
- **可測試性：** Service 層可使用模擬 repository 進行單元測試；controller 可用模擬 service 進行測試
- **可重用性：** Service 邏輯獨立於 HTTP（可被 CLI、排程作業等重用）
- **錯誤語義：** Service 層定義有意義的錯誤碼；controller 對應至 HTTP 狀態碼

**考慮過的替代方案：**
- **貧血 Controller：** 繞過 service 層，邏輯在 controller 中 → 違反 SRP，難以測試
- **Direct Controller-to-Repository：** 跳過 service 層 → 失去業務邏輯層，難以驗證
- **Active Record 模式：** 模型類同時包含資料和持久化邏輯 → 緊密耦合

**權衡：**
- **樣板代碼：** 更多類和層意味著更多代碼需要維護
- **間接：** 追蹤請求流需要跨多個函數呼叫
- **緩解：** 清晰的命名慣例（Controller 處理 HTTP、Service 包含邏輯、Repository 處理 DB）

---

### 決策 5：語意錯誤碼 + HTTP 狀態對應

**內容：**
Service 層拋出帶有語意碼的錯誤（例如 `EMAIL_ALREADY_EXISTS`、`CHARACTER_NOT_FOUND`）。Controller 捕捉並對應至適當的 HTTP 狀態碼（409、404 等）。

**理由：**
- **語言無關的錯誤語義：** 客戶端可理解錯誤碼，無需解析 HTTP 狀態
- **一致性：** 相同錯誤碼總是對應相同的 HTTP 狀態（例如 409 衝突）
- **前端清晰性：** 前端可基於錯誤碼顯示使用者友善訊息（例如「此電子郵件已被註冊」）
- **除錯：** 錯誤碼在日誌中持久化，即使被中介層包裝的 HTTP 狀態

**考慮過的替代方案：**
- **僅 HTTP 狀態：** 客戶端必須解析狀態碼；難以區分相似錯誤（例如多個 400 情況）
- **自訂 HTTP header：** 某些框架使用 `X-Error-Code`；不如在回應主體中標準

**錯誤碼對應範例：**
```
SERVICE ERROR → HTTP STATUS
EMAIL_ALREADY_EXISTS → 409 Conflict
INVALID_EMAIL → 400 Bad Request
UNKNOWN_USER → 400 Bad Request（故意模糊存在性檢查）
CHARACTER_NOT_FOUND → 404 Not Found
FORBIDDEN → 403 Forbidden
UNKNOWN_SERVER_ERROR → 500 Internal Server Error
```

### 決策 6：密碼雜湊責任分工

**內容：**
Auth-service 負責在發送至 user-service 前雜湊密碼。User-service 永遠不雜湊或驗證密碼；它儲存發送的內容。

**理由：**
- **封裝：** Auth-service 擁有認證邏輯；user-service 是無狀態的
- **簡化：** User-service 不需要 bcrypt 依賴或安全專業知識
- **靈活性：** 雜湊演算法可在 auth-service 中更新，無需改動 user-service
- **當前實現：** Auth-service 發送 bcrypt 雜湊的密碼至 user-service；user-service 按原樣儲存

**考慮過的替代方案：**
- **User-service 雜湊：** User-service 引入 bcrypt，進行雜湊 → 違反分離（認證邏輯在多處）
- **共用祕鑰/金鑰：** 服務協調雜湊 → 增加複雜性

**權衡：**
- **責任清晰性：** Auth-service 必須記住此契約（無文檔風險）
- **緩解：** 此設計文檔編纂責任；spec 檔案強制執行

**已知風險：**
如果第三個服務呼叫 user-service 直接（不經過 auth-service），它可能發送明文密碼，它們會被無雜湊地儲存。目前透過網路隔離緩解（user-service 僅接受 localhost 呼叫）。

### 決策 7：短期 + 長期記憶（兩層回憶）

**內容：**
對話使用兩層記憶系統：
1. **短期：** 所有未摘要訊息（新鮮、完整的上下文）
2. **長期：** 儲存在 Qdrant 向量庫中的摘要訊息批次（用於語義相關性）

**理由：**
- **相關性：** 短期確保最近事件被準確記憶；長期提供過去主題的背景
- **上下文窗口效率：** LLM 提示不會無限增長（訊息在約 50 條後摘要）
- **RAG 好處：** 向量相似搜尋尋找主題上相關的歷史（例如「記得我們何時談論凝視？」）
- **學習價值：** 展示生產 AI 系統如何處理長對話

**考慮過的替代方案：**
- **滑動窗口：** 僅保留最後 N 條訊息 → 失去重要背景故事
- **立即摘要所有訊息：** 無短期原始歷史 → LLM 失去細微差別
- **無摘要，無限上下文：** LLM 令牌限制使其對長對話不可行

**權衡：**
- **複雜性：** 兩層系統需要 chat-service 和 ai-service 之間的協調
- **摘要品質：** 自動摘要可能失去重要細節或誤解意圖
- **延遲：** RAG 查詢為每個回覆增加 ~200-1000ms
- **Qdrant 依賴：** 引入另一個外部服務（向量資料庫）

---

### 決策 8：SQLite + Prisma 針對所有後端服務

**內容：**
所有後端服務使用 SQLite 搭配 Prisma 7 ORM 和 libSQL 適配器。

**理由：**
- **簡化：** 無需執行 PostgreSQL；單一檔案資料庫用於開發
- **學習軌跡：** 初學者更容易理解；無資料庫伺服器管理
- **Prisma 7 生態：** 展示現代 ORM 模式（型別安全查詢、遷移）
- **libSQL 適配器：** 使用 sqlite 相容 WASM 引擎，避免原生依賴問題

**考慮過的替代方案：**
- **PostgreSQL：** 對學習專案來說過度，增加操作開銷
- **MongoDB：** 複雜化關係建模（角色與使用者的關係、訊息與對話）
- **原始 SQL：** 失去 Prisma 的型別安全和遷移工具

**權衡：**
- **並發：** SQLite 不適合高寫入競爭；每個服務得單執行緒存取
- **擴展：** 無法分片資料；每個服務受單機儲存限制
- **備份：** 需要檔案層備份；無內建複製
- **可接受用於：** 學習專案、示範、小使用者群

**生產遷移（如果需要）：**
可透過以下方式切換至 PostgreSQL：
1. 更新 `prisma/schema.prisma`：`provider = "postgresql"`
2. 更新 `.env`：`DATABASE_URL = "postgresql://..."`
3. 重新執行遷移：`npx prisma migrate deploy`

---

### 決策 9：Vanilla JS 前端（無框架）

**內容：**
所有前端應用使用 vanilla JavaScript 搭配 Vite，無框架（React、Vue 等）。

**理由：**
- **學習目標：** 展示 HTTP 通訊、DOM 操作、JWT 處理，無框架抽象
- **最小依賴：** 減少套件大小和 npm 生態風險
- **直接瀏覽器 API：** 學生直接學習 fetch()、localStorage、DOM 方法

**考慮過的替代方案：**
- **React/Vue：** 更快的開發、更好的可擴展性，但隱藏重要概念
- **TypeScript：** 會為學習專案增加編譯複雜性

**權衡：**
- **開發速度：** 無元件重用；更多 UI 模式樣板
- **可維護性：** 更大的前端變得難以除錯，無框架結構幫助
- **團隊規模：** 不適合大型團隊（框架結構幫助協調）
- **可接受用於：** 小型前端、學習內容

---

### 決策 10：OAuth / 第三方認證超出範圍

**內容：**
認證僅限於電子郵件 + 密碼。OAuth（GitHub、Google 等）未實現。

**理由：**
- **範圍：** 學習專案專注於核心認證機制（密碼雜湊、JWT），不是第三方整合
- **簡化：** 消除外部認證供應商的依賴
- **自我包含：** 使用者可以離線測試系統，無需供應商 API

**考慮過的替代方案：**
- **OAuth2 整合：** 增加 ~500 行程式碼、外部依賴

**權衡：**
- **使用者便利：** 使用者必須記住另一個密碼（無社交登入）
- **安全性：** 密碼管理是使用者責任（密碼重用風險）
- **未來增強：** OAuth 可添加至 auth-service，無需觸及其他服務

## 風險 / 權衡

### 風險 1：服務間網路呼叫
**情境：** Auth-service 呼叫 user-service 建立使用者。如果 user-service 關閉，註冊失敗。

**嚴重性：** 中（打破註冊功能）

**緩解：**
- 新增指數退避重試
- 在 gateway 上實現健康檢查以偵測失敗服務
- 未來：使用斷路器模式優雅地降級

---

### 風險 2：無分散式交易
**情境：** Auth-service 雜湊密碼，呼叫 user-service 儲存。User-service 崩潰，接收後發生但未提交。密碼雜湊丟失；使用者無法再次登入。

**嚴重性：** 低（罕見，使用者可重新註冊）

**緩解：**
- 實現冪等性：auth-service 包含唯一請求 ID；user-service 拒絕重複插入
- 新增稽核日誌以偵測並手動恢復孤立的操作
- 未來：Saga 模式或兩階段提交用於複雜工作流

---

### 風險 3：如果後端暴露，密碼明文風險
**情境：** User-service 意外暴露至網際網路（DNS 誤設定、防火牆規則錯誤）。攻擊者呼叫 `/users` 端點直接，傳送明文密碼，無雜湊儲存。

**嚴重性：** 嚴重（密碼洩露）

**緩解：**
- 強制執行網路層隔離：user-service 僅綁定 127.0.0.1（localhost）
- 防火牆規則：阻止入站至連接埠 3000、4000、5000、6000、6001
- 註冊端點速率限制
- 未來：新增密碼驗證規則（最小長度、複雜性）

---

### 風險 4：摘要品質降級
**情境：** AI 生成的摘要遺漏重要情節。角色行為在摘要後變得不一致。

**嚴重性：** 中（降級使用者體驗，非關鍵）

**緩解：**
- 微調 LLM 摘要提示以強調「關鍵決策和角色發展」
- 保持低摘要閾值（50 條訊息）以保留細節
- 生產中的手動摘要審查（對小量可行）
- 未來：允許使用者新增手動註記至摘要

---

### 風險 5：向量資料庫單點故障
**情境：** Qdrant 關閉。RAG 查詢失敗。角色無法存取長期記憶。

**嚴重性：** 低（降級，不破壞系統）

**緩解：**
- 實現回退：如果 RAG 查詢失敗，ai-service 繼續使用僅短期記憶
- 新增 Qdrant 連接健康檢查
- 未來：複製 Qdrant 資料至多個實例

---

### 風險 6：JWT 祕鑰同步
**情境：** Gateway 的 `JWT_SECRET` 與 auth-service 的不同。所有令牌驗證失敗。

**嚴重性：** 高（打破所有人的認證）

**緩解：**
- 祕鑰在 `.env` 中集中管理；兩個服務讀取相同值
- 啟動指令碼驗證祕鑰相符
- 管理儀表板（未來）以原子地輪換祕鑰
- 當前：團隊紀律；此文檔記錄要求

---

## 實現順序

1. **API Gateway** — 確保 JWT 驗證、CORS、路由正常運作
2. **Auth + User 服務** — 測試註冊、登入、密碼雜湊流程
3. **Character 服務** — 驗證 CRUD 操作、擁有權檢查
4. **Chat 服務** — 實現對話和訊息儲存
5. **AI 服務** — 整合 LLM 生成，測試短期提示
6. **RAG 整合** — 新增 Qdrant 向量儲存，測試摘要

## 部署考量

### 本地開發
- 所有服務在 127.0.0.1 上執行
- SQLite 資料庫建立於 `./prisma/dev.db`
- Ollama + Qdrant 在 Docker 容器或本機進程中執行

### 生產部署（未來）
- 服務部署至分別的雲實例或 pod
- 防火牆隔離後端服務；僅 gateway 公開
- 祕鑰（JWT_SECRET、DB_URL）從安全保管庫注入
- 遷移透過 CI/CD 管道在服務重啟前應用
- 監控：健康檢查、結構化日誌、分散式追蹤（OpenTelemetry）

## 開放問題

1. **排程作業：** 定期任務（例如清理舊摘要）應如何執行？Cron 作業在 ai-service 中，或分別的排程器服務？
2. **使用者刪除級聯：** 刪除使用者時，相關角色和對話也應被刪除嗎？目前未定義。
3. **角色發佈：** 使用者是否應能發佈角色供他人聊天？需要畫廊/發現 UI。
4. **對話分支：** 使用者應能「撤銷」並重試角色的回覆嗎？需要訊息版本化。
5. **前端令牌刷新：** JWT 在 7 天後過期。前端應自動刷新嗎？（需要 auth-service 上的刷新令牌端點）
